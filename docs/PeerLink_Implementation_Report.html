1. Executive Summary & Architecture

1.1 Project Purpose & Scope Boundary

PeerLink is a secure, closed-campus peer-to-peer exchange network where university students discover verified peers for academic tutoring, lab assistance, creative design, technical debugging, and campus collaboration.

In accordance with university capstone specifications, the project deliberately avoids complex, heavy third-party web frameworks (such as React, Angular, or Django) in favor of a clean, performant, native web stack: Node.js, Express.js, MySQL, HTML5, CSS3, and Vanilla JavaScript.

1.2 Core Architectural Principles

Stateless REST API

Clean resource-oriented routing with JSON contracts. Authentication via secure JWT tokens supported both through HTTP-only cookies and Authorization Bearer headers.

Dual-Mode Database Engine

Transparently runs against production MySQL with connection pooling, while offering a zero-dependency in-memory mock engine for offline development, automated grading, and isolated CI testing.

Strict IDOR Security

Never trusts client-supplied user identifiers. Server-side middleware verifies that actions on listings, profiles, and service requests match the authenticated session's token.

Modular Team Ownership

Clean extension points, shared conventions, and documented controller interfaces enabling 5 subsequent team members to build without code collisions or merge conflicts.

2.2 Relational Database Schema & Seed Integrity

  • users: Stores user_id, unique university_id, bcrypt password_hash, role (student/admin), and verification_status (PENDING/VERIFIED/REJECTED).
  • student_profiles: 1:1 foreign key with users; stores full name, department, academic year, bio, and avatar placeholder.
  • categories & skills: Normalized taxonomy containing 10 university disciplines (Programming, Design, Academic, Languages, etc.) and categorized skills.
  • student_skills: M:N associative junction mapping students to skills with proficiency ratings (BEGINNER, INTERMEDIATE, ADVANCED).
  • service_listings: Service offerings linked to providers, categories, skills, availability descriptions, and status (ACTIVE, PAUSED, CLOSED).
  • service_requests: Connects requesters, providers, and listings with message records and state transition tracking.

3.2 Dedicated Student Verification Portal (admin.html & admin.js)

Verification is critical for campus safety. Administrators have a dedicated governance console:

Administrator Verification Workflow

  1. Role-Guarded Entry: Only accounts with role = 'admin' (e.g. ADMIN001 / Password123!) can access /admin.html. Student accounts are intercepted and redirected.
  2. Live Metric Telemetry: Real-time stat cards calculate count of Pending Review, Verified, Rejected, and Total campus accounts.
  3. Tabbed Status Filtering & Instant Search: One-click tabs for Pending Review, Verified, Rejected, and All, coupled with a real-time search filter matching student names, University IDs, or departments.
  4. One-Click Status Mutation:
    • Clicking ✓ Verify Student immediately fires PATCH /api/auth/users/:id/verify with { status: 'VERIFIED' }.
    • Clicking ✕ Reject flags the account as REJECTED.
    • Status badges and metrics update dynamically without page reloads, accompanied by toast confirmation alerts.

4.2 Long-Term Platform Modules (Capstones Phases 8–15)

1. Real-Time Peer Chat (WebSocket)

Once a service request is marked ACCEPTED, a real-time messaging channel opens between the requester and provider. Includes message persistence, unread counters, and typing indicators via Socket.io.

2. Ratings, Reviews & Trust Score

Upon request completion (COMPLETED), both peers can submit 1–5 star ratings and written reviews. Generates a campus trust score to highlight top student mentors.

3. Physical Equipment Borrow / Lend

An extension of the marketplace for physical resources: scientific calculators, lab equipment, camera lenses, and textbooks, featuring due-date tracking and overdue status flags.

4. Content Moderation & Reporting

A student reporting mechanism for inappropriate listings, spam, or misconduct. Feeds into an administrative moderation queue for temporary suspension or banning.

5. Institutional SSO / Email Verification

Automating student verification prior to administrative review via university email OTP confirmation (e.g. @university.edu domain check) or institutional SAML/CAS SSO integration.

6. Production Deployment & DevOps

Containerization with Docker Compose (Node.js + MySQL 8.0 + Nginx reverse proxy), automated GitHub Actions CI/CD pipeline, and SSL termination.
